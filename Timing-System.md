# Timing System

## The staged chain (VERIFIED)

Ignition timing is computed in stages — no single combine function. Each stage is emulator- or code-confirmed:

**Stage 1 — Base Timing E/F blend → [0xFFFFA238]** (CERTAIN)
Records 0xB38B4 (E) and 0xB38D0 (F) are looked up via dispatcher @0xBEA18 (@0x81F3E–0x81F6A), combined with an `fmac` blend, and stored to [0xFFFFA238]. E @0xCCED4 / F @0xCD010, both 7×16 u16BE, ×0.1°. F carries more advance than E at every cell. Blend weight is **VERIFIED** (not MODEL): mode bytes are always 0, so the blend always takes the KBW[0] path — w=clamp((KBW[0]−A)/(B−A),0,1), blended=w·E+(1−w)·F. The fmac itself is code-confirmed.

**Stage 2 — Protection factors, multiplicative** (HIGH)
@0x8229A computes [0xFFFFA220/A224/A228]; @0x8242C applies `(input ± [0xFFFFA230]) × factor × K`. The applier was initially misread as an ECT warmup applier — corrected 10-19.

**Stage 3 — Knock correction, additive** (CERTAIN)
True spark summing point is **@0x4ADCE**: `[0xFFFF8798] = [0xFFFF879C] + [0xFFFF87C8] + [0xFFFF8800]` (emulator-verified). [0xFFFF8800] (fine-learned) and [0xFFFF87C8] feed the sum; [0xFFFF879C] is a knock-system retard accumulator / RPM-trim cell (≤12.03°, reads 0.0 at cruise — **refuted** as a base-timing carrier 10-19). Real retard application point: @0x47D74 → [0xFFFF85A4]. (@0x45DE8 is a stack spill, not a sum.)

**Stage 4 — IAM** (HIGH)
@0x4B86A: `fr6 = [0xFFFF87C4] × [0xFFFF30F0]` — IAM is a **multiplier**, not an adder (corrected 10-19 after the shdis fop-swap bug was found).

**Honest gaps:** the [0xFFFFA238]→[0xFFFF87C8] forward link is unmapped (all three A238 readers are monitors). Timing arbitration block **@0x45AA4** tail-publishes four per-cylinder spark candidates, with [0xFFFF8798] the dominant cruise carrier — but the candidates die there: **[0xFFFF8460..0xFFFF846C] have zero ROM-wide readers** (SPARKOUT 10-19, six independent methods; spark advance has no ROM-visible path to any timer compare — coil drive is dwell-driven only). The old "emulated cruise total 20.18° vs logged 37–40°" framing is **dead 10-19**: T8470 showed the 20.18° was a cold-RAM transient (cycles 2–3 of the [8470] ramp) — steady state is [8460] = **−46.5°**, not a budget to reconcile. The emulated side is closed (negative); what remains is the logged side — cruise really logs 37–40°, and its live source is back open. The physical IGT driver: @0x5B00 was **refuted** as an ignition scheduler 10-19 (it's a CAN receive-mailbox scheduler — the old claim rested on a decoder bug); the crank path does not drive spark (CRANKISR). The staged application sites are certain; the terminal hop is **documented negative (IGNOUT 10-19):** the true ignition output chain is mapped end-to-end — driver **@0x8978** (OS boot-task, called once from the @0xDCE6 init chain via task table @0xDE74) + dwell-setter **@0x8714** (called via jsr from the dwell computer **@0x4C908** — true entry, not @0x4C910): **@0x4C908 → @0x8714 → @0x8B2A → @0x8D94 → GR2x/OCR2x**, emulator-driven with byte-identical spark 10°→40° differentials. But **no spark-advance value reaches any compare register through any ROM-visible path** — while dwell DOES drive the compare registers directly: the **@0x8C48 tail writes `u16[OCR2x] = C + mirror/2`** at 0x8D32 (delay slot of `bra`), **overwriting** @0x8D94's OCR2x — linear, slope 1/2, all 4 cylinders, emulator-validated (DWELLFLOW 10-19; the tail was missed earlier because rdis.py misdecoded `fmov.s fr3,fr4` as a nop). This overturns the two negatives the wiki cited: IGTEVENT §3 ("no reader feeds a dwell-derived value to any ATU-II compare register") and IGNOUT §2 ("dwell only GATES the @0x8D94 call, not a compare operand") — dwell gates @0x8D94 AND drives OCR2x through the tail. The spark→IGT value chain still does not exist in ROM; the last mile must be call-timing-vs-crank or hardware, both outside static value flow. **But the chain is runtime-vacuous (DWELLTRIG 10-19):** the dwell output stage @0x8B2A/@0x8C48 has **no periodic runtime trigger** — reachable only via boot-originated paths, and the one dispatch chain that could reach it (@0x4CC0C→walker) is **broken at the dispatch table**: it cannot select walker B (**@0x4C908**, the sole caller of the dwell setter @0x8714). Walker B is dead code (emulator-confirmed: the dispatch selects walker C or the stub, never walker B). So "whenever the setter runs, the chain runs" is true but empty — the setter never runs after boot. (Entry-point corrections owned: @0x8B2A not @0x8B2C, @0x8A00 not @0x8A10, @0x86A8 not @0x86B0 — the modules push registers *before* the prologue; same class as the @0x7744-vs-@0x7740 mistake. Also @0x89FE, @0x86FE, @0x8978 — each 2–16 bytes earlier than first reported.)

## Advance formula (VERIFIED 10-19)

Fully decoded leaf function @0x4D02E: `advance[ch] = float(wrap(30·byte[0xFFFF8888] − 10°))/65536` — Q16.16 crank degrees over the 720° cycle. The slot byte is a 30° crank-slot index (0–23). Writer **FOUND 10-19:** @0x4CC0C, called by the boot/init sequencer @0x503DC via `jsr @r2` through pool 0x504F4. It's a write-once boot-time constant — 4 boot-gated readers only; the [0xFFFF85A4]→[0xFFFF8888] link is dead. Firing order **1-3-2-4**, confirmed from the ROM table at 0x6D7CC (`00 02 01 03`) — not assumed. IGT pin-to-channel mapping still open. Advance is also expressed as task phase via software-DSTR.

## B3 protection chain

Three kill mechanisms analyzed; two stand:
1. **Mode bytes always 0** — init zeroes them, no writer exists. Blend always takes the KBW[0] path. (VERIFIED)
2. **Cross-wired relay** — writer m→bit m vs consumer m→bit (m+3)%4; inert at every mode. (VERIFIED)
3. ~~Zeroed threshold~~ — **VOIDED** (thresholds are power-on-indeterminate, not cleared).

**B3 High-RPM Timing table** (8×7 @0xCC6C8, 7.4°–34.4°) is live-looked-up but **computed-but-discarded** — the channel is inert downstream. Modeled, never applied.

## Dwell (definition-complete 10-19)

Table @0xDD4C4 (16×5, X=RPM, Y=battery V), scaling x*0.004 ms derived from the ROM timer config. Clock tree corrected 10-19: TCR2A/B=0x04 (not 0x00), one-shot linkage armed. Dwell mirror [0xFFFF4224] has exactly one ROM writer (the dwell reader @0x8E10, delay-slot store) — equation fully characterized, emulator-validated. **Resolved 10-19:** Pφ' = **10 MHz** is now grounded (TICKRATE — two independent init paths), closing the old 2× absolute-ms crystal uncertainty. Relative shape is ROM-exact. Coil drive is **not** dwell-derived: the ATU-II coil-drive GRA/OCR values are timer-relative constants/ROM bytes, never computed from the dwell table (IGTCHAIN). **The dwell computer itself is orphaned (CALL4C910 10-19):** its true entry is **@0x4C908** (not @0x4C910), and a ROM-wide census finds exactly **one reference** to it in the entire ROM — the u32 at **0x6DF44** (+12 field of a stride-16 dispatch-table entry at 0x6DF38). The four static dispatch sites all read entry+0 only — but **DYNJSR 10-19 found @0x4C908 sitting at index 3 of that same ROM function-pointer table (0x6DF38[3])**, reachable in principle via indexed dynamic `jsr @rN` at sites 0x4CF68/0x4D0E2 (entry [0] → @0x4C8F2 was observed live under emulation; index-3 reachability is **unproven** — RAM-state wall). First *potential* runtime path to the dwell computer, not proven. Nothing calls the dwell computer through any proven path; its periodic re-arm trigger is not in ROM. The boot task @0x503DC → jsr @0x4CC0C runs **once at boot**, not periodically. Definition-complete but un-triggered.

**But the dwell→compare value path is real (DWELLFLOW 10-19, refuting the old "GATE, not a compare operand" claim):** the @0x8C48 tail writes **`u16[OCR2x] = C + mirror/2`** at 0x8D32 (delay slot of `bra`), overwriting @0x8D94's OCR2x — linear, slope 1/2, all 4 cylinders, emulator-validated end-to-end ((RPM,Vbat)→mirror→OCR2x monotone). Two paths inside @0x8B2A/@0x8C48: (1) the gate — `fr3 = 30·(u32[0xFFFF4214+4i] + mirror·16)/(float)u32[0xFFFF4230]`, `fcmpgt` at 0x8BE2 gates the @0x8D94 arm call; (2) the compare drive — the tail write. **The output stage is boot-only (DWELLTRIG 10-19):** exhaustive caller census (all modes: bsr/bra/pool+jsr/jmp/.long-any-alignment/movi20/mova/task-tables) plus emulator validation found **zero periodic runtime trigger** for @0x8B2A/@0x8C48 — reachable only via boot-originated paths. The dispatch chain that could theoretically reach it at runtime (@0x4CC0C→@0x4CE8C/@0x4D0A0→walker→@0x8714→@0x8B2A) is **broken at the dispatch**: the ROM dispatch table cannot select walker B (@0x4C908) — walker B is dead code. **The missing drivers aren't hiding elsewhere either (REGION9XXX + JSRCLEAN 10-19):** 0x9000–0x9FFF is real code (22 prologue fns + leaf stubs, pool→jsr only) with **zero references** to any orphaned site, and a 16,524-store RAM function-table write hunt found **zero** installing 0x9xxx/@0x4C908 pointers. A 14,803-site jsr @rN census (77.2% resolved, triple-sourced with the bsr census and RAM-table census) found no hidden callers — the no-periodic-trigger negative is now triple-sourced. (6 of the 12 "zero-caller" 0x9xxx functions are label artifacts — and @0x9280/@0x9164 have `jmp @rN` tail-callers (ISR dispatcher stubs at 0xED00/0xED1C) that the jsr-only census missed; genuinely caller-less is down to **4**: @0x9A50, @0x9B30, @0x9D5C, @0x9E38. DYNJSR 10-19.)

## Scheduler tick (measured 10-19, interrupt model refuted)

Tick period **524.288 ms** — ATU-II channel 11 on φ'/16 (TCR11=4), TCNT11 free-runs from 0, compare-match at GR11A=0xFFFF (reset value — GR11A/B are never written). 65536 counts at 125 kHz. **Corrected 10-19 (ABSSCALE):** the earlier 104.8576 ms figure implicitly assumed φ'=10 MHz with Pφ=50 MHz (out of spec, contradicting the 120e6 constant) — the true period is **5× longer**. Every "104.8576 ms"/"625 kHz"/"209.72 ms" derivation was 5× too fast. Pφ = **10 MHz CONFIRMED** from three independent lines (120e6 integer-K factorization → K=1; dwell scaling TCR8=0x44 → φ'/16 = 125 kHz → dwell_ms = raw×0.004 — the inherited x*0.004 stands; spec-range chip ID rules out SH7058S), so the dwell 2× uncertainty stays collapsed — only the tick number dies. The counter hardware is fully configured — but **the tick interrupt does not exist as a live mechanism (refuted 10-19, TIER11EN): no TIER11 writer exists anywhere in ROM** (five independent static methods plus a dynamic cross-check; zero stores to 0xFFFFF5CC — and the sweep provably rediscovers all 6 known ch11 accesses, so the machinery works). The hardware reset value of TIER11 is already 0x0000, so the "reset already enables it" variant is dead too. **The IMI11A/B compare-match interrupts can never fire on this ROM.** The old model — "dwell-refresh task rec6 every 2 ticks = 1048.576 ms, the knock sequencer and warmup task ride rec6's rate" — is dead, and the TIER11 "cable target" is moot (logging cannot confirm a nonexistent writer). Whatever actually drives the cyclic tasks (knock sequencer @0x504FC — which MODE889A identifies as **Task-3's big sub-dispatcher**, not the OS scheduler, and which RUNENTRY 10-19 proves runs **at most once per boot** (a conditional init dispatcher called exactly once from @0xDD1A — the old "@0x504FC is the periodic scheduler" claim is refuted; note 0xDD0E is a fall-through label inside @0xDCE6, not an entry) — warmup task @0x34414, ADC task @0xDCA8) is a different, unidentified mechanism. The periodic trigger is an open question again — **but the hiding spots are closed (REGION9XXX + JSRCLEAN 10-19):** the missing drivers are not in 0x9000–0x9FFF (real code, zero references to any orphaned site) and not installed by ROM-visible RAM table writes (16,524-store hunt: zero installing pointers). The no-hidden-caller negative is triple-sourced (bsr census + jsr @rN census + RAM-table census). (Correction: the true ISR entries are @0xEAF2/@0xEB60, vectors 184/186 — the earlier @0xEAF8/@0xEB66 was 6 bytes into the prologue.)

## Crank ISR (traced 10-19, refined)

True entry **@0x7740** (not @0x7744 — the ROM's prologue starts 4 bytes earlier), reached via **@0x74A8 ← @0xEA28** — and @0xEA28 is **+2 inside the CMI10B ISR @0xEA26**, not a dispatcher (EA28TRIG 10-19). Its sole trigger is **hardware vector 178 (CMI10B — ATU-II channel-10 compare-match B)** via trampoline @0x282C. **Rate contested 10-19 (unresolved inter-report tension):** EA28TRIG measured "1 CMI10B per 256 TI10 rising edges" (emulator-validated — but with stubbed peripherals), while ABSSCALE shows the TI10 event-counter path is **DISABLED**: TCR10=0x00 (CKEG=00 = "TI10 input disabled"; the firmware at 0x75B4–0x75BC does a read-modify-write PRESERVE, not a program), TIER10=0x0000 (init explicitly clears bits 0,1,3). @0x7AA4's OCR10B writes execute but the counter never counts and the interrupt never fires — crank RPM actually comes via **channel-0 input capture (TCNT0 @ 2 MHz)**, not TI10. ABSSCALE flags "what actually drives @0x7740" as open for the crank-chain owners; the TI10 rate is **not settled fact** — do not cite it as one. Two corrections to earlier reports: the @0x74A8 gate is **inverted** — the crank path runs when byte[0xFFFF4182]==0, skipped when ≠0; and @0xEA26's tail (jsr @0x8262 / jmp @0xB718) is **abandoned** on the crank path (after @0x7F08 the firmware jumps into OS bookkeeping @0xF4B4). The ICI0A hardware vector stub only ACKs TSR0 and enters the OS task scheduler. The core reads ICR0A @0xFFFFF434, computes the 60° period **[0xFFFF4184] = NEW−OLD** (u32 wrap), and via @0x7F08 produces **[0xFFFF4160] = 120,000,000.0 / Σ₆** (emulator-verified 3/3). **The crank path does NOT drive IGT/spark** — zero reads of spark cells, zero writes to ignition timer-compare registers (exhaustive cluster scan). **[0xFFFF6988]/[0xFFFF6B00] — the live-writer paradox (LIVE6988 + RAMPTR6988 10-19, stands).** [6988] has **exactly three static writers, none live**: (1) the known boot-gated copy @0x0275D4 in @0x0275BE ([6988]←[4160], gated on byte[0xFFFF6955]==0 — and task[1]@0x270AC writes that gate byte *before* task[2] runs, so with r4=1 the copy **may never fire, even at boot**); (2) a second writer @0x027C5C in @0x027C08 ([6988]←0.0, an init-zero cascade gated on byte[0xFFFF695A]==1, zero static callers — found by a 58,219-store symbolic census that refuted RPM6988's "exactly one writer"); (3) **the boot RAM-fill loop @0x10340** (`mov.l r7,@r4`) — writes **0xC33C3CC3 (−188.2374)** across the **entire RAM** [0xFFFF0020, SP) (12,259 writes), via @0x10326 ← @0x10062 ← rec5 stub @0xD7D0 (emulator-verified: seeded [6988]=1234.5 → overwritten). **Method lesson (bears on the tripwires):** point-value store censuses are blind to range fills — A1 resolves each store to a single effective address, but r4 sweeps 12K values so `ea == 0xFFFF6988` never fires. Any future "zero writers" verdict must also sweep fill-loop patterns (`mov.l rX,@rY` + `add #4,rY` + backward branch). **Yet the live code genuinely consumes [6988] as RPM: 81 live scheduler tasks read it at 55 distinct PCs per pass** (fuel/spark/DBW/knock table lookups — the heavy live paths) **and write it 0 times**; [0xFFFF4160] (live crank RPM) has only 5 reader functions. The contradiction is sharp and bounded: the engine runs, 55 reader PCs consume [6988] every pass, no live writer exists under an exhaustive census. [0xFFFF6B00] has **no writer anywhere** (static + dynamic). Do not treat [6988] as a boot snapshot live code ignores — it is the live RPM source, and its writer is the paradox. (Unresolved inter-report tension: DISARM says @0x270AC *zeroes* byte[6955]; RPM6988 says it writes f(r4) — LIVE6988 adds a [695A]-gated init function but settles neither [6955] claim.)

### Crank-core SKIP flag + supervisor task (mapped 10-19, T4182 + SUPERVISOR)

**byte[0xFFFF4182] is the crank-core SKIP flag** (T4182 10-19, emulator-validated): nonzero = the @0x74A8 gate **skips** the @0x7740 crank ISR core; zero = the core runs. Exactly two writers:

- **W1 @0x7378** — runtime setter inside `set_4182 @0x7360`: `byte[4182] ← r4` (new value), executed in a branch delay slot so it always fires on the change path; notifies `@0x317C(r4=0xB0)` iff the new value == 1. Sole caller: a tail-`jmp @r2` at **0x271ac** from supervisor task **@0x27184**.
- **W2 @0x73de** — boot init inside `@0x73bc`: `byte[4182] ← 0` as part of straight-line zeroing of the crank state bytes (4180/4181/4182/419C/41A1/41A3), called once from the boot init sequencer (@0xD87C `jsr @r1` in a long `jsr` chain).

**The supervisor task @0x27184 (SUPERVISOR 10-19)** is 12 instructions computing `desired = NOT(byte[0xFFFF694D]==1 OR byte[0xFFFF6984]==1 OR u16[word[0xFFFF2200]]!=0)` — it mirrors the result to byte[0xFFFF6959] and tail-calls set_4182(desired). (Correction to T4182's anchor, emulator-confirmed: the run condition is **u16[word[0xFFFF2200]]==0**, not s16<0 — `extu.w` zero-extends before `cmp/ge`, so word=0xFFFF skips.) The three inputs' writers are found: **byte[0xFFFF694D]** ← @0x2707E (supervision-inhibit countdown — reload from @0xBE9A8 lookup @0xB1B7C when checks pass: f32[6988]<~0, byte[6902]==1, byte[694E]==0; decremented otherwise); **byte[0xFFFF6984]** ← @0x274B4/@0x2750C (scheduler-inhibit flag); **the voter behind it (T2154 10-19):** byte[0xFFFF2154] has four confirmed writers (@0x21c78/@0x21c32 → 0x00; @0x21f62/@0x21EA0 → 0x00 gated; @0x21fa2 → 0x01 gated; @0x221be → 0x00 gate-failure paths), all `mov.w r0,@Rn` word stores of @0xBEAF0(x)-packed values. Chain [2154]→[6984] via @0x274DA (4/4 emulator cases). **Corrected vote formula (emulator-verified, fixes SUPERVISOR §3b's input-passthrough model):** byte[6984] ← 1 iff **(byte[2154]==0 || byte[24BC]==1 || byte[33D8]==0), else 0** — a pure boolean vote, no input passthrough. One open candidate: the @0x4E3FC range-fill loop could write byte[2154] iff dispatcher @0x4E3F2 is entered with r14 ≤ 0xFFFF2154 (zero static callers — RAM-dispatched; falsification needs a RAM snapshot, Nov 6 cable); **dword[0xFFFF2200]** ← @0x274C6/@0x2752E = `(cnt<<16)|(~cnt&0xFFFF)` (redundant scheduler tick counter — the supervisor needs counter==0xFFFF). @0x317C(r4=0xB0) is the OS "raise IPL to 11" critical-section primitive, fired on skip-engage. **Driver OPEN:** @0x27184 has **zero static references ROM-wide** — it belongs to a trio of RAM-dispatched tasks {@0x27130, @0x27184, @0x27440}; boot emulation stalls at a hardware wait-loop (0xC4E) before the scheduler starts, so the dispatch rate/address are unestablished.

## What the drive logs say

Cruise timing logs 37–40° while E/F tables max out near 30° at those points. The 7–10° gap matched the +8.0° fine knock-learning limit almost exactly — and the mechanism is **CONFIRMED real** (KNOCKADV 10-19): the knock system demonstrably learns positive advance (+8.0° cap, +6.0° learned → +6.000° on all four per-cylinder publishes in a cruise differential test). But the cruise attribution is **IAM-constrained, not unconditional**: the positive authority is **(1−IAM)×[0xFFFF87C4]**, enforced every knock cycle by @0x4C022 — at IAM=1.0 a seeded +6.0° learned cell is destroyed → 0.000° in one cycle. So the gap can be [0xFFFF8800] **only if IAM<1 at cruise**; at IAM=1 it must be IAM×[0xFFFF87C4]. (The "emulated cruise total 20.18°" it was once measured against was a cold-RAM transient — cycles 2–3 of the [8470] ramp; steady state [8460]=−46.5°.) The gap's true source is still open (see [Drive-Log-Findings](Drive-Log-Findings.md)).
